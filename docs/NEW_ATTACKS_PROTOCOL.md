# Protocol: does Stackelberg transfer to two attacks nobody has measured?

**The claim.** A defender with only mechanism priors can choose a response close to the measured best for an attack it has never
seen, and does so at least as well as a hand-written playbook. **The test.** Two new attacks, `ssdp_reflection` and
`telnet_scan_outbound`. Their priors and playbook entries are written and frozen *before* any response to them is measured; then
all ten responses are measured three times per attack; then each policy is graded on regret (best measured response minus the
chosen one). The success criteria are fixed in the same file, in advance.

Stackelberg does not learn from the measurements. It decides from the frozen priors alone; the measurements are the answer key.

## Why this is believable

| Threat to the result | What stops it | Where it shows up in the report |
|---|---|---|
| Priors written after seeing results | priors committed, then frozen, then pushed; GitHub records the push and a PR comment with its own clock | E3, E4 |
| A response measured before the freeze | the freeze refuses to run if any row exists; the first logged run must start with 0 rows; the pre-freeze smoke test applies only ALLOW | E5, E11 |
| Code or priors tweaked after the freeze | sha256 of every deciding, generating and grading file in FREEZE.json; measurement and analysis refuse to run on a changed tree | E1 |
| A bad run quietly discarded and repeated | every run, failed or not, is a record in a hash-chained log; the rows file hash must match the last record | E6 |
| A row edited afterwards | the chain; the rows commit; recomputation from the raw rows | E6, E10, E12 |
| Tuning on the old benchmark | its sha256 is frozen | E9 |
| A forged clock | NTP status is recorded; GitHub's timestamps do not depend on the VM's clock | E13, E4 |
| The author had already seen results | **cannot be proven**: a written declaration plus the order of the timestamps | E2 (and the limits section) |

The evidence report (step 9) is generated by a script from these artefacts. Nothing in it is typed.

## Steps

Roles: the **author** is a person who has not seen any measurement of the new attacks (a teammate, or Abdullah if no one else is
available and they say so). The **operator** has sudo on the VM. Claude's part is the tooling; Claude has seen the whole benchmark
and does not write priors.

| # | Who | What | Command | Time |
|---|---|---|---|---|
| 1 | done | Tooling, tests, template, this protocol | `pytest tests/test_new_attacks_*.py` | - |
| 2 | operator | Check the clock; blind-safe smoke test (ALLOW only: the generators work and each baseline is at least 3 packets) | `timedatectl` then `sudo .venv/bin/python3 -m iot_defense.experiments.new_attacks.smoke` | about 3 min |
| 3 | author | Read `docs/NEW_ATTACKS_BLIND_AUTHOR_BRIEF.md`; fill in `config/experiments/new_attacks/preregistration.yaml`; set `status: READY` | `python -m iot_defense.experiments.new_attacks.prereg validate` | 1 to 2 h |
| 4 | operator | Commit and push the filled file as its own commit | `git add config/experiments/new_attacks/preregistration.yaml && git commit -m "Blind priors and playbook for the new attacks" && git push` | 1 min |
| 5 | operator | Freeze: writes FREEZE.json (refuses on a dirty tree or if any row exists); commit and push it; then post its commit hash as a PR comment (GitHub timestamps it) | `python -m iot_defense.experiments.new_attacks.prereg freeze`, commit, push, `gh pr comment 1 --body "Pre-registration frozen at <freeze commit sha>"` | 3 min |
| 6 | operator | Measure: 3 blocks x 11 responses x 2 attacks = 66 rows. Refuses unless the freeze is intact, the tree is clean and HEAD is pushed | `sudo .venv/bin/python3 -m iot_defense.experiments.new_attacks.measure --reps 3` | about 13 min |
| 7 | operator | Commit the raw rows and logs (they are git-ignored, so force-add), push, post their sha256 as a PR comment | `git add -f data/experiments/new_attacks/rows.jsonl data/experiments/new_attacks/run_log.jsonl data/experiments/new_attacks/smoke_log.jsonl` | 2 min |
| 8 | operator | Grade | `python -m iot_defense.experiments.new_attacks.analyze` | seconds |
| 9 | operator | Generate the evidence report and open `data/experiments/new_attacks/evidence_report.html` | `python -m iot_defense.experiments.new_attacks.evidence --server` | seconds |
| 10 | optional | Three more blocks per attack, graded separately, as independent confirmation | `sudo .venv/bin/python3 -m iot_defense.experiments.new_attacks.measure --reps 6 --phase confirmatory`, then steps 7 to 9 | about 13 min |

The time for step 6 comes from the benchmark itself: its blocks for attacks of 5 to 9 seconds took 80 to 140 seconds each (for
example 89 s for data exfiltration and 138 s for DNS amplification), so about 7 minutes for `ssdp_reflection` (9 s attack) and 5 for
`telnet_scan_outbound` (6 s attack). Step 3 is the long and the important one.

## What each possible outcome means

- **Both pass.** Stackelberg, from priors written before measurement, chose within the pre-registered regret of the best response and
  no worse than the playbook, on two attacks it had never seen. State it as that: two for two, alongside the leave-one-attack-out result.
- **One fails.** Report it, with the report's table of how wrong the priors were. That is a finding about the priors, not a reason to rerun.
- **Both fail.** Equally publishable, and equally the true state of the evidence.
- The pre-registered criteria are never changed afterwards. A change is a new experiment with a new freeze.

## If something goes wrong

- A generator needs a fix after the smoke test: fix it **before** step 5 (the freeze); the fix is then frozen with everything else.
- A measurement run crashes: the failure is already in the log; fix the cause only if it is not in a frozen file, otherwise it is a
  new experiment. Re-running resumes at the first incomplete block (finished blocks are kept).
- Any change to a frozen file after step 5 makes `measure` and `analyze` refuse to run. That is the point.
